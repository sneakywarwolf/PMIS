User guide

Day-to-day use of PMIS for testers, Team Leads, AVPs and Admins.

"Within scope" means projects the user leads, or projects whose tester belongs to the user's team. Permissions are enforced by the server, not just hidden in the interface.

The table shows the defaults. An Admin can change them under Settings > RBAC, which lists every feature covered by access control (63, in 10 groups: Dashboard, Projects, Findings, Vulnerability Database, Reports, Report Templates, Quiz, Users, Retention, Updates) with a switch per role for AVP, Team Lead and Tester. Admins always have every feature, and the switch for Admin is locked on. The Settings panel is not a feature: it is only ever available to Admins. A switch decides whether a role may use a feature at all; the scope rules above (own projects, own team) still apply on top of it. Changes apply to everyone as soon as they are saved, and a menu item or button disappears for a role that has lost the feature. Reset to defaults restores the table above.

Projects

  1. Open Projects and choose New project.
  2. Choose the compliance category (VAPT, PCI, CERT-In or ASV) and the testing type: Web, API, Mobile, Thick Client, Network or SCR.
  3. Fill in client, scope, dates, testing environment and the report details. These are entered once and reused in every report. Client SPOC fields appear for CERT-In projects. SHA-1 is asked for Mobile, Thick Client and SCR projects.
  4. SCR projects also ask for the Code Location and the Scanning System Username and Hostname (printed as {Code Location}, {system username} and {system hostname}), and do not ask for Testing Approach or Types of Login System.
  • Status updates automatically: Not started when created, In progress when the first finding is added, and Completed when a report is generated.
  • Compliance status (Compliant, Non-Compliant, In-Progress) is set by you and printed in reports.
  • Completed projects stay editable by authorized users. Every field change is recorded, and Team Leads, AVPs and Admins can see the change history on the project page.
  • Press Ctrl+K to search projects you can open.
  • Hover tips throughout PMIS appear after one second.

Findings and evidence

  1. On a project, add a finding by choosing a vulnerability from the library, so the standard wording is reused.
  2. Add the project-specific details: affected URLs or hosts, authentication type, dependencies and notes.
  3. If the library's CVSS score does not fit, set an override score and vector for this finding.
  4. Add numbered proof-of-concept steps. A reminder asks you to make sure no sensitive information is included in screenshots or steps. Each step has a description and one or more screenshots (PNG, JPG, GIF or WebP, up to 20 per step). Screenshots print under their step in the order shown, which you can change with the arrows, and each one gets a thin black border in the Word report.
  5. On Network projects the steps and PoC section is hidden for VA findings: the evidence comes from the Nessus scan output.

Findings that are not in the library

  • Both options below are buttons in the Add Finding dialog, next to Cancel and Continue.
  • Add Manually: enter the vulnerability yourself: name, severity, CVSS score and vector (a calculator is built in), description, impact, remediation, reference and optional CVE and CWE IDs. The finding is created in this project at once.
  • Sync Vuln DB (a slider, on by default): also sends the vulnerability to the library as a normal approval request. The finding stays usable whatever the decision, and nothing is published without approval. Switch it off to keep the finding in this project only; there is no later sync for it.
  • Import Project Findings: add many findings as PT findings (in a Network project they appear under PT Findings) from a .csv or .xlsx file (up to 100 MB and 5,000 rows) using the sample template’s exact headers. The optional Affected Instances column (4th; one host or URL per line in the cell) fills the finding’s Affected Instances for the reports; files without it still import. The i beside the button lists the accepted files and the exact header row. You see a preview first; if any row is invalid, nothing is imported. Rows already in the project are skipped. Imported findings stay in this project only: they never enter the library and have no sync option. Workbooks with formulas, macros or embedded objects are rejected.

Both kinds are treated like findings picked from the library: they need steps and screenshots before a report, and they appear in the project’s reports and Issue Log only.

Report readiness: a finding is ready for a report only when it has at least one step, every step has a description, and every step has a screenshot. The finding list shows which findings still need work. Nessus findings on Network projects are exempt, because their evidence comes from the scan output.

Network projects and scan imports

Network projects support vulnerability assessment (VA) and penetration testing (PT) activities, and three kinds of import:

ImportAccepted filesResult
Network scope.txt, .csv, .xlsxThe list of in-scope hosts. The import button shows the supported formats and column headers.
Nessus.nessus, .csvA preview of the scan's findings. You choose which plugins to import as VA findings. Re-importing a plugin adds its new hosts to the existing finding. Files up to 500 MB are accepted; the file is read while it uploads and is not stored, only the findings you import are saved. A .csv must be a Nessus export with at least the Plugin ID, Name, Risk and Host columns. Include the Plugin Output column to get each host’s output as evidence; an export without it imports with no output. A CSV has no CVSS vector, so one is only proposed from the score, as for any import without a vector.
Nmap.xml, .txt, .nmapOpen ports recorded on the project for the report's port tables.

Nessus CSV files are read whatever way they were saved: commas, semicolons or tabs between columns, UTF-8 or UTF-16 text, and stray control characters in plugin output (replaced by a space). Only a file with binary data at its start, or without the Plugin ID, Name, Risk and Host columns, is refused, with a message saying why. If an upload fails, the message says whether the connection dropped while uploading, or the server stopped after the whole file had arrived, and a Try again button repeats the check.

  • Nessus findings belong to that project only. They are not added to the shared vulnerability library.
  • All VA findings imported into a project can be deleted together with Delete All VA Findings.

SCR (Secure Code Review) projects

SCR is a Testing Type (Platform) that uses the same project fields as a Cert-In Application project. Two imports are available on its Findings page:

  • The project's Details page shows the imported Site Map below Tools Used.
  • Fortify findings belong to that project only and are not added to the shared vulnerability library. Delete All Fortify Findings removes them together.
  • For PCI and VAPT, upload the template with SCR as its Activity Type. For Cert-In, upload a template with SCR as its Activity Type; an SCR project never falls back to the Application template.
  • SCR reports leave the CVSS score and vector placeholders empty.

Vulnerability library

  • When someone submits a new vulnerability, Admins, AVPs and Team Leads get a notification. Clicking it opens the Pending Approval tab and highlights that request; if it has already been reviewed you are told so. Only those roles can open the tab or read pending records, whatever the link says.
  • Everyone can search, filter by severity and export the library as CSV.
  • New entries: Testers and Team Leads submit a request. It stays pending until an Admin, AVP or Team Lead approves it. The requester is notified of the decision.
  • Edits: Testers propose changes to an existing entry. The original stays unchanged until the request is approved.
  • Admins can add, edit or remove entries directly. They can also bulk upload a CSV or XLSX file in one of two modes: Replace swaps the whole library; Merge adds to it and asks which version to keep when names clash. Download the sample file from the page for the exact column format.

Dashboards, notifications and live users

  • Dashboard: Testers see their own work, Team Leads their team, and AVPs and Admins the whole organisation.
  • Notifications: the bell shows library decisions, new users, assignments, system updates and quiz reveals. Selecting a notification opens the related page. An Admin chooses, per notification type, which roles (AVP, Team Lead, Tester) receive it under Settings > Notifications. Admins always receive all of them.
  • Live users: the count next to System Online. Admins, AVPs and Team Leads can open a list of active and idle users within their scope.

Cyberdigest

The Cyberdigest menu item is a daily cybersecurity digest for the team. It collects news and research, checks every CVE against the official records, and shows each item with its source and how far it has been verified. The aim is a trustworthy view, not a long one: anything that cannot be supported is left out or labelled, never presented as fact.

Sources

  • Discovery (what happened): The Hacker News, BleepingComputer, Cyber Security News, the PortSwigger blog and research feeds, and the Cloudflare blog. An article proves that a publisher reported something, not that it is true.
  • Authoritative (what is true): the CVE Program (cve.org), the NIST National Vulnerability Database and the CISA Known Exploited Vulnerabilities (KEV) catalog.
  • Not covered: CERT-In advisories. CERT-In publishes no machine-readable feed, so they are not included, and every digest says so.

What each tab shows

  • Daily digest: the day’s summary: confirmed zero-day alerts, new KEV additions, new or updated CVEs, news (the same incident under several headlines is grouped, with every source link kept), PortSwigger and Cloudflare research, corrections to earlier items, and a closing list of what the digest could not cover (failing sources, items still awaiting verification). A day with nothing that qualifies says so. Items are ordered by a published policy (confirmed zero-day, then KEV, then analyst-verified, then provider severity, then recency); no numeric score is calculated.
  • News and CVEs: everything ingested, with filters (search, category, state and dates for news; vendor, provider severity, KEV and NVD status for CVEs). A CVE’s official record status, NVD enrichment and KEV listing are separate badges. Every CVSS score is shown with the provider that assigned it. Missing values stay unknown.
  • Zero-days: confirmed alerts, known-exploited vulnerabilities whose zero-day status is unconfirmed, and a review queue for reports that lack evidence.
  • Verification & source health: per-source status and last successful check, items waiting for verification or in conflict, rejections and corrections. The page never says everything is healthy while an enabled source is failing.

How an item gets its label

  • Attributed reporting, not independently confirmed is the most the system will say about an article. Verified by analyst is set only by a reviewer, and only when every CVE the article cites exists in the official record. A story citing a CVE that is rejected or unknown to CVE.org is marked Conflicting evidence, and a verified story drops back automatically if its CVE evidence turns bad.
  • Confirmed zero-day needs dated primary evidence (vendor, researcher, government or incident report) that exploitation happened, primary evidence that no fix existed at the time, a published CVE record, no contradicting primary source, and a recorded reviewer approval. A headline, a KEV listing, a public proof of concept or a missing patch is never enough on its own. If the evidence is later retracted, the confirmation is withdrawn at once.
  • Summaries are the publisher’s own words, trimmed. They are checked against the article text, and any summary that adds a CVE, score, version, date or exploitation claim not in it is dropped. No AI model is used anywhere in Cyberdigest.

Who can do what

Administrators control everything: the Administration tab, source health, verification, and every decision (verify or reject stories, record zero-day evidence, approve or withdraw, hold or withdraw a digest). Every other role is a read-only reader of published content only: no buttons, no working material (pending or conflicting items, review queue, reviewer notes, user names, source health), and the server refuses any write or administrative request from them. This is fixed in the code; it is not part of Settings > RBAC. Every decision needs a written reason and is recorded in the audit log.

Administration tab (Admins only)

  • Available to non-administrators: one switch. Off, and every non-admin request to Cyberdigest is refused by the server on its next call; the menu entry disappears within a minute and an open page shows a notice. Administrators keep access.
  • Processing pipeline running: a separate switch. Off, and nothing is collected, verified or published; existing data and published digests stay, and readers see the latest digest with its date.
  • Daily publish time and time zone (any IANA zone, default 08:00 Asia/Kolkata), publish automatically or hold for an administrator, the minimum share of healthy news sources, digest retention in days, and the retry delay for failed jobs. All values are validated by the server and every change is audited with the old and new value.
  • Approved link destinations: the exact hostnames readers may click through to. Anything else shows as plain text. blog.example.com does not allow example.com; shorteners and IP addresses are refused. Add a news feed does both in one step: the server starts collecting the feed and its website becomes clickable. Feed hosts are checked against the public internet on every connection; private and internal addresses are refused.
  • Background jobs: last success, last run and failure streak for ingestion, CVE checks, zero-days, story checks, the digest and housekeeping. Failed jobs retry by themselves with growing delays and alert the Admins.

Automatic daily digest, schedule and notifications

  • News feeds are checked every 20 to 30 minutes and the KEV catalog about every 45 minutes. CVEs mentioned in stories are looked up on CVE.org and NVD in the background and rechecked daily.
  • The digest is built and published automatically once a day after the configured time, with no click from anyone and no login needed. It publishes only if the checks pass: the verification pass succeeded, the KEV catalog has been retrieved, and enough news sources are healthy. If a source is down the digest says how many were checked (“only 3 of 6”). If the checks fail, nothing is published, the job retries by itself, and readers keep seeing the previous digest with its age. A restart or missed run is caught up on the next tick, and a digest can never be created twice for a day. When everything was checked and nothing qualifies, a “no qualifying updates” digest is published. Everyone gets an in-app notification.
  • A published digest is never edited. If a story or zero-day in it is later rejected or withdrawn, the digest shows a correction flag on that item and the next digest lists the correction. An Admin can withdraw a whole digest. Old digests are removed after the retention period; the newest one is always kept.
  • Admins are notified when a source or a background job fails repeatedly, once a day while it lasts, and again when it recovers. All Cyberdigest notification types can be switched per role in Settings > Notifications.
  • Admin bulk actions (optional, nothing depends on them): Approve selected for zero-day cases whose evidence qualifies, and Verify selected for stories. Each item is still checked on its own and refused if it does not qualify.
  • Security: links open only on a click, only to approved hostnames over https, in a new tab with no referrer. There is no redirect or proxy route, nothing in articles is fetched or rendered as HTML, and the page loads no third-party images, scripts or frames. See CYBERDIGEST-SECURITY-AUDIT.md in the repository for findings and residual risks.
  • Optional environment settings: NVD_API_KEY raises the NVD request limit. CYBERDIGEST_REQUIRE_SECOND_APPROVER=1 stops the person who recorded zero-day evidence from also approving it. CYBERDIGEST_DIGEST_TIME and CYBERDIGEST_DIGEST_MODE (hold or auto) only seed the first-run values; after that the Administration tab is the only place they change. To limit what the server can reach, also restrict the backend container's outbound network to the feed hosts and DNS.

Retention

PMIS deletes old data automatically, once an hour, under two Admin-configurable policies in Settings:

WhatDeleted after (default)Counted from
Completed projects, with their findings and files365 daysReport generation
PoC screenshots90 daysWhen the PoC step was created, whatever the project's status

The Retention page shows when each completed project is due for deletion. Download the reports you need before that date.

After its screenshot is removed, a finding is no longer report-ready, so the project cannot generate a new report until screenshots are re-added. Generate reports within the screenshot retention period, or have an Admin adjust it.

Quiz

  • Admins schedule security quiz questions. Each question can be answered for 24 hours after it goes live.
  • After the reveal you see the answer and explanation for questions you attempted. Late answers are recorded but not scored.
  • The scorecard shows your points, streaks and badges. Leaderboards rank players and teams, and Team Leads can rename their team.

Admin tasks

  • Users: create, edit, bulk upload (CSV or XLSX), reset passwords and reactivate accounts. Reset users must set a new password at next sign-in.
  • Deleting a user deactivates the account immediately. Reactivating within 24 hours restores it with its data. After 24 hours, the data and files of projects the user owns are purged permanently.
  • Templates: see Reports.
  • Temporarily locked accounts (Admin only, at the top of User Management): accounts locked after too many failed sign-ins, with name, email, role, the reason, when the lock started, when it ends and a live countdown. Unlock User asks for confirmation, removes the lock at once and records who did it in the activity log. The person still needs their password. Locks end by themselves; the list updates without a refresh. How many failures lock an account (3 to 20) and for how long (1 to 240 minutes) is set under Settings > Security; a change applies to later locks, and accounts that are already locked keep their unlock time.
  • Settings: application name, logo and favicon (browser tab, sidebar, login page), colours, table density, rows per page, severity names and colours (also printed in reports), session timeout, password policy, retention periods, storage and database size quotas (enforced: uploads are refused at the storage quota; creating or changing data is refused with HTTP 507 at the database quota, while viewing, deleting and Settings keep working), the largest file allowed for each accepted upload format (Attachments), which roles get which notifications, which roles may use each feature (RBAC), Issue Log columns, and date, time and number formats. Every setting takes effect for everyone once saved. Every change is recorded, with the person’s name and role, in the settings history.
  • Updates: the About page shows the running version and newer releases. On a Docker installation, update by following Upgrading.
