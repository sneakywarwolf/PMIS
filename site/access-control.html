Access control and security

Who can do what, how users sign in and stay signed in, and the request-level controls the backend applies.

Roles

  • ADMIN: full administration, templates, catalogue approval, settings, update scheduling.
  • AVP: senior reviewer. Organisation-level dashboards and approvals.
  • TEAM_LEAD: leads a team of testers. Reviews team projects and catalogue requests.
  • TESTER: runs engagements, adds findings, requests catalogue entries and proposes edits.

Testers are linked to a Team Lead through assignedTlId. Team Leads can have a manager through managerId. Data visibility is limited by these links and by the project access rules in the service layer.

Authentication

  • Sign-in: accepts a username, or an email address (exact match, then case-insensitive match).
  • Password hashing: Argon2id, memory cost 65536 KiB, time cost 3, parallelism 4.
  • Password policy: minimum length defaults to 14 and complexity defaults to required. Both are set in the Admin settings and checked on password change.
  • Forced change: new users and users given a temporary password must change it at next sign-in. A forced change does not ask for the current password.
  • Lockout: after MAX_LOGIN_ATTEMPTS failed attempts (default 5), the account is locked. The message says 15 minutes. Failure counts are kept in Redis per username.
  • Deactivated users cannot sign in. Deactivation has a 24-hour grace period, after which owned project data and files are purged, per the endpoint description.
Not found in the code: a "Remember me" option. The login request accepts only username and password. Token lifetimes are fixed as described in the next section.

  • One active session per user: a new sign-in replaces the previous session. A refresh token from the replaced session is rejected.
  • Inactivity: the session expires after the configured idle period. Refresh does not revive an idle session.
  • Password change revokes all of the user's refresh tokens.
  • Logout revokes the current refresh token and clears the active session.

Request hardening

  • Security headers (Helmet): Content-Security-Policy restricting default sources to self; Referrer-Policy: no-referrer. HSTS is sent only when COOKIE_SECURE=true.
  • Frontend headers: CSP, X-Content-Type-Options: nosniff, X-Frame-Options: DENY, and a restrictive Permissions-Policy, set in next.config.js.
  • No-store: every API response is sent with Cache-Control: no-store.
  • Cross-site writes: state-changing requests that the browser flags as cross-site are refused with 403. This check is in addition to SameSite=Strict cookies.
  • CORS: only the origin in FRONTEND_URL, with credentials.
  • Validation: a global validation pipe with whitelisting and rejection of unknown properties.
  • Body size: JSON and URL-encoded bodies are limited to 1 MB.
  • Timeouts: request timeout 120 seconds, header timeout 30 seconds.
  • Swagger: served at /api/docs outside production. In production it is off unless ENABLE_SWAGGER=1.
  • Startup check: in production the backend refuses to start if a JWT secret is unset or still starts with CHANGE_ME. It warns if a secret is shorter than 32 characters or if the two secrets are equal.

Rate limits

Fixed one-minute windows in Redis.

Signed-in user, all routes300 requests per minuteRATE_LIMIT_PER_MIN
Anonymous, by IP (login, refresh)30 requests per minuteAUTH_RATE_LIMIT_PER_MIN
Heavy routes, per user20 requests per minuteHEAVY_RATE_LIMIT_PER_MIN

Heavy routes are: Nessus preview and import, PoC image upload, Nmap import, report generation, template upload, Issue Log, catalogue export, and both bulk uploads. Exceeding a limit returns 429 with Retry-After.

Fails open: if Redis cannot be reached, requests are allowed. This is a deliberate availability choice in the code.
Per-IP limits depend on the proxy: the backend trusts X-Forwarded-For from loopback and private addresses. The code comment notes that clients can spoof this header unless a reverse proxy overwrites it. Brute-force protection on login still applies per username.

Uploads and imports

  • Size cap: every multipart upload is limited to 25 MB while streaming.
  • Bulk CSV or XLSX (users and catalogue): 10 MB maximum. The file type must match its content. A CSV containing binary data is rejected.
  • XLSX checks: macro projects, embedded objects, ActiveX and external links are rejected. Cell formulas are rejected. The workbook may have at most 500 internal entries and 100 MB declared decompressed size.
  • PoC images: the type is detected from the file's magic bytes, not the client MIME type. Accepted types are PNG, JPG, GIF and WebP. Objects are stored under a poc/ prefix with a random ID.
  • Downloads: report files are served only through signed links that expire.

Audit logging

Sign-ins, sign-outs, password changes, user, project, template, report, catalogue, settings and quiz actions write rows to audit_logs with actor, target, details, IP address and user agent. Retention settings and an Admin view of the audit log are not described in these pages because no read endpoint for it was found in the controllers.
