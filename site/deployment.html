Production & operations

Run PMIS for a team: HTTPS, configuration, backups, upgrades and a checklist to complete before go-live.

What runs

docker compose up -d starts five containers on a private Docker network:

ContainerPurposeReachable from outside
frontendWeb interface. Forwards API calls to the backend internally.Yes, on FRONTEND_PORT
backendApplication server. Applies database migrations on every start.No
postgresDatabase (PostgreSQL 16)No
redisSessions, background jobs (Redis 7)No
rustfsObject storage (RustFS, S3-compatible) for templates, reports and screenshots. Its web console is disabled in production (details).No

Data is kept in three Docker volumes: postgres_data, redis_data and rustfs_data. Docker prefixes them with the project name, for example pmis_rustfs_data when the folder is named PMIS. Check with docker volume ls.

HTTPS with a reverse proxy

PMIS serves plain HTTP. Put a reverse proxy in front that terminates TLS.

  1. Bind the web interface to the local machine only, so it can't be reached around the proxy. In .env: 
    FRONTEND_PORT=127.0.0.1:3000
  2. Set the public address and secure cookies in .env: 
    FRONTEND_URL=https://pmis.example.org
COOKIE_SECURE=true
  3. Configure the proxy. Example for nginx: 
    map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl;
    server_name pmis.example.org;
    ssl_certificate     /etc/ssl/pmis/fullchain.pem;
    ssl_certificate_key /etc/ssl/pmis/privkey.pem;

    client_max_body_size 512m;   # Nessus scans up to 500 MB; every other upload is far smaller

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;   # replace, don't append
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
    }
}
    The proxy must set X-Forwarded-For to the real client address, replacing any value the client sent, as above. Redirect port 80 to 443.
  4. Apply the changes: docker compose up -d.

Sign-in protection settings

The backend container receives only the variables listed above. To change sign-in lockout or request-rate limits, create docker-compose.override.yml next to docker-compose.yml. Compose reads it automatically.

services:
  backend:
    environment:
      MAX_LOGIN_ATTEMPTS: "5"         # failed sign-ins before a temporary lock
      RATE_LIMIT_PER_MIN: "300"       # requests per minute per signed-in user
      AUTH_RATE_LIMIT_PER_MIN: "30"   # sign-in requests per minute per address

The values shown are the defaults. Lower them for stricter protection.

In-application settings

Session timeout (default 15 minutes), password policy, retention periods, branding and report formats are changed by an Admin under Settings. They are stored in the database and recorded in the settings history.

Backup and restore

A complete backup has three parts: the database, the files volume and your .env. Backups contain client vulnerability data. Encrypt them and restrict access.

Commands below are for Linux, macOS or Git Bash, run in the PMIS folder. Replace pmis_rustfs_data with your volume name from docker volume ls. For the most consistent file copy, back up while nobody is uploading, or stop the stack first with docker compose stop.

Back up

# Database
docker compose exec -T postgres pg_dump -U pmis pmis > pmis-db-$(date +%F).sql

# Files (templates, reports, screenshots)
docker run --rm -v pmis_rustfs_data:/data:ro -v "$PWD":/backup postgres:16.4-alpine \
  tar czf /backup/pmis-files-$(date +%F).tgz -C /data .

# Configuration (keep with the backup, store securely)
cp .env pmis-env-$(date +%F).bak

Restore

Restoring replaces all current data. docker compose down -v permanently deletes the current database and files. Back up first if you are unsure.
docker compose down -v
docker compose up -d postgres
docker compose ps postgres          # wait until it shows (healthy)

docker compose exec -T postgres psql -q -U pmis -d pmis < pmis-db-YYYY-MM-DD.sql
docker run --rm -v pmis_rustfs_data:/data -v "$PWD":/backup postgres:16.4-alpine \
  tar xzf /backup/pmis-files-YYYY-MM-DD.tgz -C /data

docker compose up -d

Use the same .env that was in place when the backup was taken.

Versions and the About page

  • Installed version. The backend reports APP_VERSION, which the release workflow sets in each backend image to the release tag it was built from (for example 1.0.10). If it is not set, as when you build from source, the version in package.json is shown instead, and that number is not changed for each release. The About page reads this one value; the frontend has no separate version.
  • Latest version. The About page asks the GitHub Releases list of sneakywarwolf/PMIS (override with UPDATE_REPO, or UPDATE_API_URL for a mirror). Drafts, prereleases and tags that are not plain dotted numbers are ignored. If GitHub cannot be reached or answers with an error, the page says it could not check and keeps the last good result.
  • Installing updates from the About page is off by default. It only works when you set UPDATE_COMMAND, a command you provide that the backend runs when an Admin schedules an update. The standard Compose files do not set it, so on a standard install you upgrade as described below. PMIS does not download, verify or roll back anything itself: that is up to your command, so pin versions or digests there. Only an Admin can schedule or cancel an update, and the release text is never passed to the command.

Upgrading

  1. Back up. If you are upgrading from a version that used MinIO for file storage, also follow Migrating from MinIO to RustFS: the files have to be copied across once.
  2. Get the new version: 
    # Prebuilt images: set PMIS_VERSION in .env to the new release, then
docker compose pull
docker compose up -d

# Built from source:
git pull
docker compose up -d --build
  3. Database migrations run automatically when the backend starts. Watch with docker compose logs -f backend until it reports healthy in docker compose ps.

Migrating an existing install from MinIO to RustFS

Earlier versions stored files in MinIO. RustFS cannot read MinIO's on-disk format, so the files have to be copied across over the S3 interface. A new install does not need this.

Take a backup first, and keep the old MinIO volume until you have checked the result. The commands are for Linux, macOS or Git Bash, run in the PMIS folder.
  1. Set the values for your install. PROJECT is the prefix of your storage volume's name: run docker volume ls | grep minio_data, and for pmis_minio_data the project is pmis. OLD_IMAGE is the MinIO image you ran before, the value of your old MINIO_IMAGE setting: 
    PROJECT=pmis
OLD_IMAGE=minio/minio:latest
KEY=$(grep '^MINIO_ROOT_USER=' .env | cut -d= -f2-); KEY=${KEY:-pmisminio}
SECRET=$(grep '^MINIO_ROOT_PASSWORD=' .env | cut -d= -f2-)
  2. Stop the old stack, which keeps its data. Get the new version, then start only the new storage: 
    docker compose down
git pull
docker compose up -d rustfs
  3. Start the old MinIO on its old data volume: 
    docker run -d --name pmis-old-minio --network "${PROJECT}_default" \
  -e MINIO_ROOT_USER="$KEY" -e MINIO_ROOT_PASSWORD="$SECRET" \
  -v "${PROJECT}_minio_data":/data "$OLD_IMAGE" server /data
  4. Create the bucket on the new storage, copy every file across, and compare. The new storage has no bucket yet, because PMIS creates it only when it first starts. mc diff prints nothing when the two sides match: 
    MC="docker run --rm --network ${PROJECT}_default --entrypoint mc -e MC_HOST_old=http://$KEY:$SECRET@pmis-old-minio:9000 -e MC_HOST_new=http://$KEY:$SECRET@rustfs:9000 $OLD_IMAGE"
$MC mb --ignore-existing new/vapt-reports
$MC mirror --preserve old/vapt-reports new/vapt-reports
$MC diff old/vapt-reports new/vapt-reports
  5. Remove the temporary MinIO container and start PMIS: 
    docker rm -f pmis-old-minio
docker compose up -d
  6. Open PMIS and check that an existing report downloads and an existing screenshot shows. After a few days of normal use, delete the old data: 
    docker volume rm "${PROJECT}_minio_data"

The old MINIO_IMAGE line in .env is no longer used and can be removed.

Keep the RustFS console private

RustFS ships a web console (port 9001) that signs in with the same access and secret key PMIS uses. PMIS does not need it: the backend talks only to the storage's S3 API on port 9000, over the private Docker network. Anyone who reached the console with those keys could read or delete every report, template and screenshot, so it must not be reachable by users or from the internet.

The production docker-compose.yml protects it in two layers:

  1. No published ports. The rustfs service has no ports: entry, so neither 9000 nor 9001 is reachable from outside the Docker network. Only the frontend port is published.
  2. Console switched off. RUSTFS_CONSOLE_ENABLE: "false" stops the console from listening at all, so no other container on the network can open it either. The S3 API on port 9000 is unaffected, so uploads, downloads, report generation and the health check keep working.

Check your deployment

Run in the PMIS folder with the stack running.

  1. Confirm the storage ports are not published. Both commands should print :0 (nothing mapped): 
    docker compose port rustfs 9000
docker compose port rustfs 9001
  2. Confirm the console is off and the S3 API is up. The first line should print console:000 (connection refused) and the second health:200: 
    docker compose exec -T rustfs curl -s -o /dev/null \
  -w 'console:%{http_code}\n' --max-time 5 http://127.0.0.1:9001/
docker compose exec -T rustfs curl -s -o /dev/null \
  -w 'health:%{http_code}\n' http://127.0.0.1:9000/health
  3. Confirm PMIS still works: docker compose ps shows every service healthy, then upload a template or a PoC screenshot and generate a report.

If your install predates this setting

Either pull the current docker-compose.yml, or add the variable to the rustfs service yourself and recreate it:

    environment:
      RUSTFS_ACCESS_KEY: ${MINIO_ROOT_USER:-pmisminio}
      RUSTFS_SECRET_KEY: ${MINIO_ROOT_PASSWORD:?set MINIO_ROOT_PASSWORD in .env}
      RUSTFS_CONSOLE_ENABLE: "false"
docker compose up -d rustfs

Recreating the container does not touch the rustfs_data volume. The backend reconnects on its own; if a request fails right after, run docker compose restart backend.

Never publish ports 9000 or 9001 in production, for example with a ports: entry or a proxy rule. docker-compose.dev.yml publishes both with fixed credentials and is for development only. If you must administer storage, use mc over the private network as in the migration steps, not a published port.

Production checklist

  • The four secrets in .env are unique random values, and .env is readable only by the operator (chmod 600 .env).
  • PMIS is served over HTTPS. FRONTEND_URL is the exact public address. COOKIE_SECURE=true.
  • The web port is bound to 127.0.0.1, or firewalled so that only the proxy can reach it.
  • The reverse proxy replaces X-Forwarded-For with the client address.
  • Access is limited to your organisation's network or VPN where possible.
  • SEED_DEMO=false. ADMIN_PASSWORD is removed from .env after the first start.
  • The admin password was changed at first sign-in, and each administrator has their own named account.
  • PMIS_VERSION and RUSTFS_IMAGE are pinned to specific versions.
  • The database, cache and storage ports are not published. Never use docker-compose.dev.yml for production.
  • The RustFS console is off (RUSTFS_CONSOLE_ENABLE: "false") and unreachable from outside. See Keep the RustFS console private.
  • Backups are scheduled, encrypted and stored off the server, and a restore has been tested.
  • The host operating system, Docker and PMIS are kept up to date.
